# Deploying KayGPT

Three supported targets:

| Option | Frontend | Backend | Database | Persistent files |
|---|---|---|---|---|
| A + B (recommended hosted) | **Vercel** | **Render** web service (Docker) | Render PostgreSQL | Render persistent disk, or S3-compatible storage + Chroma server |
| C | Docker Compose | Docker Compose | Postgres container | Docker volumes |

Nothing here has been deployed by the refactor itself; follow the steps and verify with the checklist at the end.

## How the pieces talk

```text
Browser ── https://kaygpt.vercel.app ──▶ Next.js (Vercel)
                                    │  /api/v1/*  rewrite (server-side)
                                    ▼
                          https://kaygpt-api.onrender.com (FastAPI)
```

The browser only ever talks to the frontend origin. Next.js rewrites `/api/v1/*` to the backend, so the session cookie is **first-party** on the Vercel domain. This avoids third-party-cookie blocking (Safari ITP, Chrome's third-party cookie restrictions), and the default `SameSite=Lax` cookie with the CSRF header is enough. FastAPI still enforces an Origin allow-list and CORS for direct calls.

`BACKEND_URL` is resolved when `next build` runs, so set it before building (Vercel env var / Docker build arg).

### Direct cross-origin mode (fallback)
If the proxy can't be used (e.g. you need streams or uploads beyond Vercel's proxy limits, see below), point the browser straight at the API:
- Frontend: `NEXT_PUBLIC_API_URL=https://kaygpt-api.onrender.com` (rebuild).
- Backend: `COOKIE_SAMESITE=none`, `COOKIE_SECURE=true`, `FRONTEND_URL=https://kaygpt.vercel.app`.
- Caveat: the cookie is then third-party and **Safari and privacy-focused browsers will block it**. A custom domain pair (`app.example.com` + `api.example.com`, `COOKIE_DOMAIN=.example.com`) makes it first-party again; that's the recommended way to run cross-origin.
- The frontend's `proxy.ts` redirect guard is disabled in this mode (it can't see the API's cookie); the client shell still redirects on 401.

## A. Vercel (frontend)

1. Import the repository in Vercel → **Root Directory: `frontend`**. Framework preset: Next.js (auto). Install command `pnpm install`, build `pnpm build` (defaults).
2. Environment variables (Production + Preview):
   | Name | Value |
   |---|---|
   | `BACKEND_URL` | `https://kaygpt-api.onrender.com` (your Render URL, no trailing slash) |
   | `NEXT_PUBLIC_MAX_UPLOAD_MB` | `20` (match the backend's `MAX_UPLOAD_SIZE_MB`) |
   | `NEXT_PUBLIC_API_URL` | leave unset (same-origin proxy) |
3. Deploy. `output: "standalone"` in `next.config.ts` is ignored by Vercel's builder and is harmless.
4. Set the backend's `FRONTEND_URL` to the Vercel production URL. Preview deployments have other origins; add them to `CORS_ORIGINS` (comma-separated) if previews must log in.

**Proxy limits to verify on your plan.** Vercel serves external rewrites from its edge proxy, not a function, so function payload limits shouldn't apply. Vercel does document a timeout for proxied requests, and long agent runs with web search can take a while. The backend sends a keep-alive comment every 15 s, which prevents idle timeouts but not a hard total-duration cap. Test a long answer and a 20 MB upload after the first deploy. If either hits a limit, use direct cross-origin mode with a custom domain pair (see above).

## B. Render (backend)

`render.yaml` at the repository root is a Blueprint for **PostgreSQL + the FastAPI web service**.

1. Render dashboard → **New → Blueprint** → select the repo. Render creates `kaygpt-db` and `kaygpt-api`.
2. Fill the `sync: false` variables when prompted:
   - `GOOGLE_API_KEY`, `TAVILY_API_KEY` (both required in production; the app refuses to start without them)
   - `FRONTEND_URL` = your Vercel URL, `BACKEND_URL` = the Render service URL
   - `SECRET_KEY` is generated by Render.
3. What the blueprint does:
   - Builds `backend/Dockerfile` (Python 3.12, uv-locked dependencies, non-root user).
   - `preDeployCommand: alembic upgrade head` runs migrations before each release takes traffic. The container's own migration step is disabled with `RUN_MIGRATIONS=false`.
   - Uvicorn with `--proxy-headers` (correct client IPs for rate limiting) and 1 worker by default (`WEB_CONCURRENCY`).
   - Health check: `GET /api/v1/health`.
   - `DATABASE_URL` comes from the managed database; `postgresql://` URLs are switched to the psycopg 3 driver automatically.
   - LangGraph checkpoints live in the same PostgreSQL database (tables created at startup).
   - Logs are JSON lines (one per request plus errors) with a `request_id`; conversation content is not logged.

### Persistent storage on Render (important)
Render's filesystem is **ephemeral**: anything written outside a persistent disk is lost on every deploy and restart. KayGPT writes two kinds of files:

| Data | Default location | Production options |
|---|---|---|
| Chroma vector index | `CHROMA_PERSIST_DIRECTORY=/data/chroma` | (1) persistent disk, (2) a Chroma server (`CHROMA_MODE=http`, `CHROMA_HOST`, `CHROMA_PORT`, `CHROMA_SSL`) such as a separate Render private service with its own disk, or Chroma Cloud |
| Uploaded files | `UPLOAD_DIR=/data/uploads` | (1) persistent disk, (2) `STORAGE_BACKEND=s3` with any S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, MinIO): `S3_BUCKET`, `S3_ENDPOINT_URL`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` |

The blueprint uses option (1): a 5 GB disk at `/data` on a paid instance. A disk-attached service runs as **one instance** with **no zero-downtime deploys** (brief downtime on each deploy). To scale horizontally, switch to S3 storage + a Chroma server, then remove the disk and raise the instance count. Also note that the in-process rate limiter is per instance.

PostgreSQL is the source of truth: if the Chroma index is lost or the embedding model changes, rebuild it from a Render shell:
```bash
python -m scripts.reindex            # memories from Postgres, documents from stored files
```
Uploaded files themselves can't be regenerated; back up the disk (Render disk snapshots) or the bucket.

### Updating
Push to the tracked branch → Render builds the image, runs migrations, swaps the instance. Roll back from the Render dashboard (and `alembic downgrade` if a migration must be reverted).

## C. Docker Compose (full stack)

```bash
cp .env.example .env          # set GOOGLE_API_KEY, TAVILY_API_KEY (and SECRET_KEY for production-like runs)
docker compose up --build     # http://localhost:3000
```
Services:
- `postgres` (16-alpine) with volume `postgres-data` and a `pg_isready` health check.
- `backend`: runs migrations on start (`RUN_MIGRATIONS=true`), then uvicorn on :8000. Volume `backend-data` at `/data` holds Chroma and uploads. Health check on `/api/v1/health`.
- `frontend`: Next.js standalone server on :3000, built with `BACKEND_URL=http://backend:8000`; starts after the backend is healthy.

Compose runs the backend with `APP_ENV=development` by default (local cookies over plain HTTP). For a production-like run behind TLS, set `APP_ENV=production` and a real `SECRET_KEY` in `.env`, and terminate HTTPS in front of the frontend (e.g. Caddy, nginx or a cloud load balancer). `Secure` cookies require HTTPS.

Data survives `docker compose down`; `docker compose down -v` **deletes all data**.

Only PostgreSQL for local development (backend and frontend run on the host):
```bash
docker compose -f docker-compose.dev.yml up -d   # also creates kaygpt_test for the test suite
```

## Post-deploy checklist

1. `GET https://<api>/api/v1/health/ready` → `database: ok`, `vector_store: ok`.
2. Register on the frontend; the response sets `kaygpt_session` on the **frontend** domain (DevTools → Application → Cookies), `HttpOnly`, `Secure`.
3. Send a message: tokens appear progressively (not all at once). If they arrive in one burst, something between the browser and the API buffers (check for compression or proxy buffering).
4. Ask something time-sensitive → "Web search" chip appears (Tavily key works).
5. Upload a PDF → status goes to Ready; ask about it.
6. "Remember …" in one chat, "recall …" in a new chat.
7. Redeploy the backend, then confirm conversations, documents and memories are still there (persistence works).
8. Long answer (> 60 s with web search) and a near-limit upload through the Vercel proxy (see proxy limits above).
